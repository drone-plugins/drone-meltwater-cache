## Research

Versions verified: cargo 1.85.0; rustc 1.85.0; Linux amd64 observed.

### How cargo resolves its cache

Cargo home defaults to ~/.cargo and CARGO_HOME overrides it; it is not the rustup toolchain directory. Relative CARGO_HOME resolves from invocation cwd, not a nested manifest directory. No native cache-only relocation exists. Official Cargo Home documentation describes registry/cache (crate archives), registry/index (registry metadata), git/db (bare git downloads), src and checkouts (reconstructible unpacked trees): https://doc.rust-lang.org/cargo/guide/cargo-home.html . `CARGO_HOME=.cache/cargo cargo fetch --locked` in /tmp/cargo-w5-fixture created that relative home, as shown by `find .cache/cargo -maxdepth 2 -type d`. Fetch and offline logs: /tmp/cargo-w5-toolchain/fetch.log and offline.log. The plugin must resolve the override against cwd even when detection finds a one-level nested lockfile. Without the override the plugin selects workspace/.cache/cargo, but builds MUST receive the variable; selection alone does not reconfigure Cargo.

### What to cache and what not

Per https://doc.rust-lang.org/cargo/guide/cargo-home.html cache registry/cache (download archives, lockfile checksums), registry/index (metadata needed offline), git/db (downloaded bare repositories, may contain private source; secure cache access required). These contain source rather than compiled machine-specific output; no cross-platform runtime verification is claimed. Exclude registry/src and git/checkouts because Cargo recreates them; exclude target (build output), rustup/toolchains (toolchain), bin (installed binaries), all home-root config/authentication/tracking/locks/SQLite metadata. Never archive the whole CARGO_HOME. `du -sk .cache/cargo/registry/*` observed cache=14808 KiB, index=3652 KiB, src=111940 KiB; removing src then running offline fetch succeeded. Growth tracks fetched dependencies; save only selected subtrees and report lifecycle overhead before claiming a performance win. Cargo file locks coordinate local writers; concurrent remote saves remain last-writer-wins (engine contract, ENGINE.md).

### Key and invalidation

Hash only committed Cargo.lock, using the existing 32-character lowercase MD5 contribution. Registry source checksums and git revisions are locked; fetch --locked rejects resolution changes (https://doc.rust-lang.org/cargo/commands/cargo-fetch.html). Missing lockfiles are not detected; no generated-lockfile fallback. Source/manifest changes alone do not change downloaded archive identity; lock updates invalidate. Registry configuration changes can lead to a cold fetch under the same key; Cargo remains responsible for source identity/checksums. Do not cache compiled outputs or claim ABI portability.

### CI integration

Restore, build and save share only workspace (ENGINE.md). Inject CARGO_HOME=<workspace>/.cache/cargo in every step; request companion change through CLI harness-core. Until it ships users must set it explicitly. Honor explicit absolute/relative overrides; do not edit project/home Cargo configuration. Global env injection also relocates configuration, credentials and installed binaries as listed in Fields; reviewers must consider that integration migration.

## Design

### Mapping entry

Append Cargo after all existing entries, without reordering them: globToDetect Cargo.lock, tool cargo, preparer newCargoPreparer(), additionalCacheDirs cargoCacheDirs. Primary path registry/cache; extras registry/index and git/db. No manifest fallback or additionalHashGlob. Mixed repositories append one lockfile MD5, intentionally causing an initial cold cache; legacy-only keys remain unchanged. This follows inspected auto_detect_util.go; tests below verify composition.

### Paths

| Path | Type | Strategy | Reason |
|------|------|----------|--------|
| CARGO_HOME/registry/cache | download | follow-only | checksummed crate archives, primary |
| CARGO_HOME/registry/index | metadata | follow-only | offline registry resolution |
| CARGO_HOME/git/db | download | follow-only | pinned git object databases |
| registry/src, git/checkouts | extracted source | exclude | reproducible from downloads |
| target, bin, config, credentials, home-root metadata | output/config/auth | exclude | nonportable or sensitive |

Cargo Home documentation and direct fetch/offline experiment are recorded in research.md. Resolve nonempty CARGO_HOME with resolveRepoPath(cwd, value), preserving whitespace as part of a filesystem path. Otherwise select workspaceRoot(dir)/.cache/cargo; no HOME fallback or config rewriting. Missing dirs are valid cold paths. HARNESS_WORKSPACE identifies shared workspace for the default; explicit relative env follows process cwd as Cargo does. Return cleaned absolute paths. No tool execution in the plugin.

## Compatibility and migration

No existing mapping entry, path or key algorithm changes (auto_detect_util.go inspection; TestScenario_Cargo_MixedLegacy characterizes composition). Existing Cargo-containing mixed repos gain one digest and incur a cold start. Build steps require CARGO_HOME; setting it globally relocates Cargo home config, credentials, installed binaries and tracking files, not just downloads. Use project-level .cargo/config.toml, CARGO_REGISTRIES_* environment authentication, and intentional PATH updates for cargo install. Do not copy credentials into the archive. This companion change requires reviewer attention; until shipped users must explicitly set the variable. Evidence: Cargo Home reference and direct relative-home fetch in research.md; harness-core gate records generated changes separately.

## Limitations

Only committed Cargo.lock and the engine's selected root/one-level project are supported; no recursive monorepo scan or lockless/generated-lock guarantee. Builds invoked from a different cwd must use absolute CARGO_HOME consistently. Home-level user config is not migrated. Git DBs can include private sources; protect cache access. No binaries, toolchains, credentials or build outputs are cached. Direct runtime validation targets Cargo/Rust 1.85.0 Linux amd64; release cross-compilation is not native Windows/macOS runtime proof. Registry download fixture does not claim public git dependency runtime coverage. Fetch/offline proves dependency consumption, not compilation speed; measured lifecycle numbers are reported by CLI test --all, not inferred. Sources and observed command logs: research.md.

Additional regression evidence: `go test -count=1 ./...` was attempted and failed in harness HTTP and storage GCS/S3 suites because this environment denies loopback connections (`dial tcp 127.0.0.1:... connect: permission denied`); see evidence/test-full.log. Infrastructure owner must enable loopback and provide the GCS emulator to rerun those suites. `go test -race -count=1 ./...` could not run because CGO is disabled (`-race requires cgo`), and `command -v cc` confirms no system compiler is installed; see evidence/test-race.log. No claim of full-suite or race success is made. Required tool-local CLI gates passed without weakening tests. No Rust compile-speed claim is made: dependency download consumption is proven by offline fetch; compilation is not cached.

Measured value from CLI metrics.env: cold fetch 0.64s, warm fetch 0.04s, offline re-extraction/fetch 0.32s, warm restore 0.02s, save 0.02s, archive 18172 KiB. Local filesystem overhead is below observed fetch savings, but fast network and tiny times make remote savings unproven; no remote performance claim. git/db was absent for this registry-only fixture and gracefully skipped (public-3-save.log: requested=3 uploaded=2 missing=1 failed=0).
