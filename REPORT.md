## Research

Versions verified: cargo 1.85.1, rustc 1.85.1 (Linux amd64).

### How cargo resolves its cache

Official Cargo home documentation below defines CARGO_HOME or otherwise ~/.cargo; relative CARGO_HOME is relative to process cwd, not the manifest directory. Observed with `cd /tmp/cargo-w6-fixture && CARGO_HOME=.cache/cargo cargo fetch --locked` using the actual 1.85.1 toolchain binaries: downloads appeared under workspace .cache/cargo. There is no separate general cache-only variable or cache-directory query. The plugin follows CARGO_HOME, otherwise selects workspace .cache/cargo as the Harness default without writing configuration. Without the variable a native Cargo invocation still uses ~/.cargo, so the variable is REQUIRED in build steps. Project native config and registry credentials are left untouched.

### What to cache and what not

Cargo home documentation recommends registry/index (metadata), registry/cache (downloaded crate archives) and git/db (bare dependency repositories). Only these three subtrees are selected. They can be absent before install; Cargo regenerates registry/src and git/checkouts. Source downloads are reusable across toolchains/OS; not claiming native Windows or macOS runtime validation. Private dependency source may be archived; cache backend access must match source access. Credentials/config/bin, target, rustup and home-level trackers/locks are never selected. Size/growth is unbounded across repeated use; actual compressed bytes and overhead will be measured by `test --all` and reported, not guessed. Cargo validates registry crates using lockfile checksums; git sources rely on their locked revisions (official Cargo home and lockfile docs).

### Key and invalidation

Use existing engine MD5(Cargo.lock), a 32-character lowercase contribution. Changed lockfile means cold key. No manifest fallback: lockless projects remain undetected. Config/source overrides can require downloads not present in the archive, but Cargo resolves/validates them itself; no build output is cached. Existing detection depth and shortest-match semantics remain unchanged. Evidence: ENGINE.md and baseline command above; changed-file scenario and public lifecycle will test this.

### CI integration

The workspace is the shared location described in ENGINE.md. Set CARGO_HOME to its absolute .cache/cargo directory for every step; harness-core gate adds injection where required. Plugin cannot export a variable into a later build container. Home side effects are listed in the machine field above and in official Cargo home documentation. No Cargo subprocess is needed in the scratch plugin image.

## Design

### Mapping entry

Append Cargo.lock / cargo / newCargoPreparer() / cargoCacheDirs after existing entries to preserve legacy-only key order (source: auto_detect_util.go inspected during research). Primary registry/index, extras registry/cache and git/db. No additional hash or per-project mode: root then one-level discovery selects shortest lockfile as existing engine does. Mixed repositories gain a final MD5 contribution and therefore a first cold run; no legacy contributions change.

### Paths

| Path | Type | Strategy | Reason |
|------|------|----------|--------|
| CARGO_HOME/registry/index | metadata | follow-only | needed for offline resolution, Cargo home docs |
| CARGO_HOME/registry/cache | download | follow-only | crates are validated/re-extracted by Cargo, Cargo home docs |
| CARGO_HOME/git/db | download | follow-only | bare locked Git dependencies, Cargo home docs |
| workspace/.cache/cargo/{same subtrees} | defaults | follow-only | matches required CARGO_HOME injection, ENGINE.md |
| registry/src, git/checkouts, target, bin, credentials and home-level locks | excluded | never selected | regenerated sources/output or sensitive state, Cargo home docs |

Explicit relative CARGO_HOME resolves from cwd, including nested projects, as observed by research fetch command; default anchors workspaceRoot(dir), not selected nested manifest. No files are written and no tool invocation occurs in preparer. Arbitrary config files are neither parsed nor modified. Preserve env spaces as part of the path.

## Compatibility and migration

Legacy-only behavior stays unchanged because Cargo is appended (mapping source and baseline evidence/baseline.log). Cargo-bearing and mixed projects get new keys and a cold run. CARGO_HOME also relocates user config, credentials, cargo install binaries and metadata for every caching-enabled step; users should retain project .cargo/config.toml, environment registry credentials and deliberate binary PATHs (Cargo home docs in research.md). The preparer does not relocate files or rewrite any configuration. Only the three approved subtrees are archived. Required local/compatibility/public lifecycle gates will establish evidence rather than treating test plans as completed results.

## Limitations

Only lockfile projects at root or one level deep are detected; shortest match wins, so independent monorepo locks do not all affect keys (ENGINE.md). Cargo fetch is dependency acquisition, not compilation; target output and toolchains remain uncached. Offline operation depends on restoring the relevant index and downloads; source overrides or changing registries may miss. Caches can hold private dependency source; access controls must match source access. Direct real-tool validation is Linux amd64 Cargo 1.85.1; cross-compilation does not establish native Windows/macOS behavior. Home trackers/locks are regenerated and can add overhead. Evidence sources: research fetch/offline commands and official Cargo home/fetch documentation; final timings and archive sizes come from the CLI lifecycle report.

## Rollout and rollback

Release through the normal drone-cache release. Projects that start being detected get a new composite key, so their first run after rollout is cold. Roll back by reverting the mapping entry and preparer; an image rollback alone does not reuse keys created by this change.
