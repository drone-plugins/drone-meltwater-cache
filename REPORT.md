## Summary

Detect committed Cargo.lock files and cache only registry/cache, registry/index and git/db under CARGO_HOME. Keys retain the engine's lockfile MD5 format; no build output, toolchain, extracted source tree or home configuration is cached. Build steps must set CARGO_HOME to the shared workspace .cache/cargo directory until the companion harness-core injection ships. Basis: research evidence/tool-observations.log, official Cargo home/environment references, and `cat internal/plugin/autodetect/auto_detect_util.go`.

## Research

Versions verified: cargo 1.85.0, rustc 1.85.0 (Linux amd64).

### How cargo resolves its cache

Official Cargo home documentation below defines CARGO_HOME, defaulting to ~/.cargo on Unix and Windows user home, and documents home config, installed binaries and dependency caches. The environment reference says relative CARGO_HOME is relative to the current working directory, not the manifest directory. The preparer follows that rule using os.Getwd, even for a nested lockfile. With no variable it returns the expected workspace .cache/cargo home; later build steps MUST receive CARGO_HOME at that same location. No native configuration is rewritten. There is no stable native cache-path query; the selected home plus documented subdirectories defines the paths. Evidence: cargo --version and isolated cargo fetch --locked, then cargo fetch --locked --offline (evidence/tool-observations.log).

### What to cache and what not

Cargo home guide recommends registry/index (metadata), registry/cache (downloaded compressed crates), and git/db (bare dependency repositories). These are source/download data, not ABI-dependent build artifacts; Cargo uses lockfile checksums and git revisions. registry/src and git/checkouts can be recreated, so exclude them. Exclude target (compiled output), rustup/toolchains, home bin (executables), config and credentials, tracker/lock databases. Never archive the entire CARGO_HOME. Private dependency sources may be included; use only appropriately isolated cache backends. Cargo coordinates its own home access; simultaneous archive snapshots and writers are not guaranteed consistent. No cross-platform runtime claim is inferred from portable source content. Evidence: official home guide; isolated fetch populated registry/cache,index,src and no target (evidence/tool-observations.log). The bat fixture has no git dependency; git/db is optional and missing paths use existing graceful autodetection. The public gate measures archive size, growth for one lockfile, and cold/warm overhead; no speedup claim precedes those measurements.

### Key and invalidation

Hash Cargo.lock only with the existing 32-character lowercase MD5 contribution. A changed lockfile invalidates downloads; unrelated source or cache directory existence does not. Locked fetch must not regenerate the lockfile. A manifest without a lockfile is intentionally not detected. Source downloads are reusable without a runtime/ABI key. Evidence: `cat internal/plugin/autodetect/auto_detect_util.go`; `cargo fetch --locked` and offline command succeeded without modifying fixture Cargo.lock (evidence/tool-observations.log).

### CI integration

Separate containers require CARGO_HOME pointing to the workspace for every step, including restore and save. Research cache_env drives the CLI public lifecycle and companion harness-core injection. Until the companion change ships users must set this variable themselves. The plugin does not export variables to other containers. A relative explicit home follows process cwd and an absolute home is honored even outside the workspace; persistence of an external home is the user's responsibility. Evidence: `cat .cursor/skills/add-build-tool-caching/ENGINE.md` and Cargo environment reference.

## Design

### Mapping entry

Append a Cargo.lock / cargo entry after existing entries, using newCargoPreparer and cargoCacheDirs for index and git/db. No manifest fallback, additional hash, exclusions or usePerProject. Existing order remains unchanged. New Cargo matches add a digest at the end of mixed-tool keys, requiring one cold run; legacy-only keys stay identical. Basis: `cat internal/plugin/autodetect/auto_detect_util.go` and the research baseline command.

### Paths

| Path | Type | Strategy | Reason |
|------|------|----------|--------|
| CARGO_HOME/registry/cache | downloaded compressed crates | follow-only | documented reusable source downloads |
| CARGO_HOME/registry/index | registry metadata | follow-only | needed for offline resolution |
| CARGO_HOME/git/db | bare git dependency source | follow-only | optional revision-addressed downloads |
| target, registry/src, git/checkouts, bin, config, credentials, trackers | output/extracted sources/executables/sensitive metadata | exclude | no entire-home archive |

Resolve explicit relative CARGO_HOME against cwd, not the detected manifest directory. No variable uses workspaceRoot(dir)/.cache/cargo, matching the required injected variable. Honor the exact nonempty environment value without trimming valid spaces. Never read or write native config. Basis: Cargo home/environment references fetched in research; path behavior tests named below.

## Compatibility and migration

Legacy-only hashes, paths and configuration stay unchanged; mixed Cargo projects get an additional lock digest and one expected cold run. No tracked files are rewritten. CARGO_HOME also moves home config, credentials, cargo-installed binaries and installation metadata; these are deliberately not archived. Keep configuration in project .cargo/config.toml, provide authentication using CARGO_REGISTRIES_* variables and preserve required binary PATH entries. Do not claim automatic migration of old home configuration. Basis: official Cargo home/environment docs and TestScenario_Cargo_LegacyCoexistence, run by create/compatibility gates.

## Limitations

Discovery remains root then exactly one level, selecting one lockfile; independent nested workspaces are not aggregated. Lockless projects are not cached; locked installs must not rewrite the lockfile. Only Cargo 1.85.0 on Linux amd64 receives real-tool lifecycle validation; cross-compilation is not native Windows/macOS validation. No compiled outputs are cached, so fetch improvements are not compilation improvements. git/db is optional and absent for the bat registry-only fixture; bare-git offline consumption is not claimed validated by that fixture. Explicit external CARGO_HOME needs user-provided shared persistence. Private sources can exist in dependency caches, so backend access must be appropriately isolated. Concurrent archive snapshots are not transactional. Basis: research tool-observations.log, Cargo documentation and the public gate metrics recorded by the CLI.

Additional regression evidence: `go test -count=1 ./...` did not pass in this sandbox: existing S3 HTTPS tests cannot connect to their loopback test server (`connect: permission denied`), recorded in evidence/full-tests.log. No S3 code was changed. `go test -race -count=1 ./internal/plugin/autodetect ./internal/plugin ./cache/...` could not start because race requires cgo (evidence/race-tests.log); the pinned Rust installer also observed no system C compiler. These supplemental checks are not claimed passed. Required CLI local, compatibility, public and cross-build gates passed; see their individual evidence logs.

## Rollout and rollback

Release through the normal drone-cache release. Projects that start being detected get a new composite key, so their first run after rollout is cold. Roll back by reverting the mapping entry and preparer; an image rollback alone does not reuse keys created by this change.
