## Research

Versions verified: cargo 1.85.0 / rustc 1.85.0, Linux x86_64.

### How cargo resolves its cache

Official Cargo home and environment references below describe CARGO_HOME (default ~/.cargo on Unix, home .cargo on Windows), which cannot be set by project configuration. Explicit CARGO_HOME wins and relative values resolve from Cargo's working directory, not the nested manifest location. `CARGO_HOME=../relative-probe cargo fetch --locked` from the ripgrep checkout created ../relative-probe/registry/cache; `cargo --version` and `rustc --version` verified 1.85.0 (log /tmp/cache-intel-cargo-w1/probe-verified.log). No project or home configuration is rewritten. Without the env the plugin returns workspace .cache/cargo children, but later build steps REQUIRE CARGO_HOME to select that home. Native registry configuration and source replacement remain Cargo's responsibility.

### What to cache and what not

Official Cargo home guidance recommends registry/index (registry metadata), registry/cache (checksum-verified compressed package downloads), and git/db (bare Git dependency downloads). These avoid ABI coupling, are reusable across fresh workspaces, and grow with dependencies/registries; private dependency source may be present, so normal cache access controls are still required. Cargo's own locking governs live writes; simultaneous stage saves are last-writer-wins, not an archive-level concurrent snapshot guarantee.
Exclude registry/src and git/checkouts because they can be regenerated, target because it is compiled output, bin and rustup because they are tools, config/credentials and Cargo home root because they may contain secrets, and global tracker/lock files because they are process metadata. Cache only the three fixed child directories, never the home itself (official Cargo home reference). `CARGO_HOME=/tmp/cache-intel-cargo-w1/probe cargo fetch --locked`, deletion of registry/src, then `cargo fetch --locked --offline` passed: downloads and index suffice (probe-verified.log). The fixture has no Git dependency: git/db remains optional, and no remote Git performance claim is made. Raw Git dependency URLs and private indexes must not embed credentials.

### Key and invalidation

Hash only committed Cargo.lock as an unchanged engine MD5 contribution (32 lowercase hex characters); lock changes invalidate, while manifests changed without updating the lock fail --locked. Downloads are not compiled output; toolchain/ABI keys are unnecessary. `auto_detect_util.go` inspected with sed establishes mapping-order composition; root or one-level shortest match remains the supported selection. Without Cargo.lock there is no detection; install-time lock generation is intentionally unsupported.

### CI integration

ENGINE.md and `cache-intel.sh help` establish separate restore/build/save steps sharing the workspace. Set CARGO_HOME to absolute workspace/.cache/cargo in all three, or an explicit shared home. Plugin cannot export a variable into another step. The harness-core gate will generate that injection; until shipped users must set it themselves. Relative CARGO_HOME follows plugin cwd just as the verified Cargo command does, including for nested manifests. Plugin does not run cargo or read credentials.

### Fixture choice

`git clone --depth 1 --branch 14.1.1 https://github.com/BurntSushi/ripgrep.git /tmp/cache-intel-cargo-w1/ripgrep` pinned SHA 4649aa9700619f94cf9c66876e9549d83420e16c. `python3` tomllib counted 61 locked packages (probe-verified.log); repository COPYING lists dual MIT/Unlicense terms. --locked fetch downloads all target dependencies deterministically without a C compiler. Value is measured by the public lifecycle gate (timings/archive/overhead in metrics.env and evidence), not inferred from restored file counts. Functional compilation is not claimed by fetch-only validation.

## Design

### Mapping entry

Append cargo after existing mappings without reordering any legacy entry: globToDetect Cargo.lock, tool cargo, preparer newCargoPreparer, additionalCacheDirs cargoCacheDirs. No additionalHashGlob or usePerProject. Legacy-only keys stay unchanged; hybrid repositories gain a trailing Cargo.lock digest. Evidence: inspected auto_detect_util.go and TestScenario_Cargo_MixedLegacy.

### Paths

| Path | Type | Strategy | Reason |
|------|------|----------|--------|
| CARGO_HOME/registry/cache | downloads | follow-only | compressed crates consumed offline |
| CARGO_HOME/registry/index | metadata | follow-only | required for offline resolution |
| CARGO_HOME/git/db | downloads | follow-only | bare Git objects; optional without Git deps |
| target, registry/src, git/checkouts, bin, config, credentials | excluded | never select | output, regenerable trees, tools or sensitive data |

Paths use explicit CARGO_HOME (relative to cwd, NOT selected nested project), otherwise workspaceRoot/.cache/cargo. Do not mutate config. Evidence: Cargo home docs and relative-probe command in research, Test_cargoPreparer_Paths and Test_cargoPreparer_PreservesConfig.

### Scenario matrix

| Scenario | Detected tools | Cached paths | Key inputs | Covered by |
|----------|----------------|--------------|------------|------------|
| single root / absent paths | cargo | three children | Cargo.lock | TestScenario_Cargo_Detection |
| one level / multiple projects | cargo once, shortest | shared home children | selected lock | TestScenario_Cargo_Detection |
| deeper than one level / manifest only | none | none | none | TestScenario_Cargo_Detection |
| explicit relative/absolute env | cargo | home children | lock | Test_cargoPreparer_Paths |

| native config, idempotency | cargo | fixed children | lock | Test_cargoPreparer_PreservesConfig |
| platform boundary | cargo downloads only | no ABI state | lock | Test_cargoPreparer_Paths; build gate (compile only) |

## Compatibility and migration

No existing mappings, keys or paths change in legacy-only repositories; mixed Cargo repositories receive an additional digest and an expected cold first run (TestScenario_Cargo_MixedLegacy). CARGO_HOME relocates config/credentials, installed binaries, metadata and locks in every caching-enabled step: use project .cargo/config.toml and registry authentication environment variables and explicitly manage cargo install PATH, as described in the official Cargo home reference in research. The plugin never rewrites tracked configuration (Test_cargoPreparer_PreservesConfig).

## Limitations

Only Cargo 1.85.0 on Linux x86_64 is directly exercised by the research commands and public lifecycle; cross-compilation is not native OS validation. No manifest-only detection, recursive discovery or per-project multi-lock hashing; shortest root/one-level lock wins (TestScenario_Cargo_Detection). Set CARGO_HOME consistently across all steps; defaults alone cannot relocate a later Cargo invocation. Fetch-only validation proves dependency consumption, not functional compilation; registry/src and git/checkouts regenerate, and target/toolchains are not cached (research probe-verified.log). Fixture has registry but no Git dependencies, so git/db performance and authenticated/private registries are unverified; never embed credentials in dependency URLs. Cache size grows and concurrent saves are last-writer-wins (Cargo home docs in research; public gate records actual size/timing).


Additional regression evidence: `go test -count=1 ./...` failed in unrelated Harness/backend tests because loopback connections were denied and the local GCS emulator was unavailable; see evidence/full-tests.log. This is an environment-blocked extended suite, not a passing full-repository test. `go test -race -count=1 ./...` could not run: Go requires cgo for -race (evidence/race-tests.log); this image has no cc, as observed during the Rust installer probe. CI infrastructure owner must provide a C compiler and accessible local backend/emulator services for these extra suites. The required skill test-local gate still passed autodetect, plugin and cache tests, vet and build (evidence/test-local.log).
