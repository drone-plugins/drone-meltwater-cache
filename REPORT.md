## Research

Versions verified: cargo 1.85.0; rustc 1.85.0; Linux amd64.

### How cargo resolves its cache

The official Cargo home guide defines CARGO_HOME, otherwise ~/.cargo (including Windows home), and its internal layout. CARGO_HOME is relative to process cwd, not a nested manifest. `CARGO_HOME=.cache/cargo cargo fetch --locked` populated that directory at fixture root with Cargo 1.85.0; `find .cache/cargo -maxdepth 2 -type d` records the layout in evidence/research-tool.log. No cache-only relocation variable exists in the environment reference below. Native .cargo/config.toml configures registries/source replacement, not this home. The plugin never reads or rewrites it and never executes Cargo. Absent CARGO_HOME it proposes workspace/.cache/cargo (build steps must explicitly set the variable until companion injection ships); explicit home values win, with relative values resolved from cwd. No unsupported claim that the default Cargo home changes automatically.

### What to cache and what not

Per the official home guide, registry/cache contains downloadable .crate archives, registry/index contains resolution metadata, and git/db contains bare dependency repositories. These are reusable source/download data, not compiled artifacts; registry archives have lockfile checksums. The index is necessary for offline resolution; git/db permits recreating checkouts. Private registries/git dependencies may put private source and repository URLs into these directories: use access-controlled caches, and never embed credentials in URLs. Normal Cargo credential files live outside these selected leaves. Do not archive the whole home: bin and toolchains are platform-specific; config.toml/config and credentials.toml/credentials may hold secrets; registry/src and git/checkouts duplicate regenerable source; target is ABI-dependent output; package lock/tracker files are local coordination metadata. The allowlist selects only the three directories, even if others exist. Sources: Cargo home guide below; observed `cargo fetch` and offline re-extraction in evidence/research-tool.log. Size depends on dependencies and can grow without bound; measure fixture size and cold/warm costs in `test --all` before making a performance claim. Concurrent Cargo writers use native locks; archives are sequential snapshots, not supported while fetch is running.

### Key and invalidation

`Cargo.lock` determines locked dependency versions and checksums; hash it with the engine existing 32-character lowercase MD5 contribution. No manifest-only fallback: libraries without committed locks are deliberately not detected. Cargo fetch --locked prevents silently changing the key input. Source edits do not invalidate downloaded data. Config/registry changes may require different data but Cargo validates source identity; users can force a custom key when isolation is required. Source: official cargo-fetch reference below and the lockfile at the pinned fixture; observed fetch --locked in evidence/research-tool.log.

### CI integration

The skill ENGINE.md and `cache-intel.sh research` existing-support inventory show CARGO_HOME not yet injected. Restore/build/save share only workspace; set CARGO_HOME to absolute workspace/.cache/cargo for all steps, not only inside the plugin. Run the CLI harness-core gate to generate that change. Until it ships this is required user stage wiring, not zero-configuration support. Explicit external homes are followed but only persist if mounted in every step. No project/native config is mutated. Side effects are enumerated above from the Cargo home guide; real toolchain binaries were installed using the official rustup installer pinned to 1.85.0 under /tmp/cargo-w3-tools and placed directly on PATH, not shims (evidence/research-tool.log).

## Design

### Mapping entry

Append an independent Cargo.lock/cargo entry after all existing entries, with newCargoPreparer() and cargoCacheDirs. No additionalHashGlob, exclusions, manifest fallback or usePerProject. This preserves every legacy-only mapping order/key; mixed repositories gain one final lockfile digest and start cold. Evidence: inspection of auto_detect_util.go via `sed -n '1,220p'` and baseline `go test -count=1 ./internal/plugin/autodetect` (evidence/baseline.log).

### Paths

| Path | Type | Strategy | Reason |
|------|------|----------|--------|
| CARGO_HOME/registry/index | metadata | follow-only | offline resolution requires the index |
| CARGO_HOME/registry/cache | download | follow-only | portable crate archives |
| CARGO_HOME/git/db | source downloads | follow-only | bare dependency repositories allow fresh checkouts |

Resolve explicit CARGO_HOME from os.Getwd(), not detected nested manifest; default workspaceRoot(dir)/.cache/cargo matches required injected value. Never create directories or mutate config. Return primary index plus cache and git/db regardless of existence, letting graceful autodetect skip missing optional git data. Evidence: research-tool.log and Cargo home guide linked in research.md. Default without env is a proposal, not Cargo's native home; required wiring is documented.

## Compatibility and migration

No existing mapping is reordered or modified; legacy-only keys and paths remain identical (baseline.log; TestScenario_Cargo_MixedLegacy and CLI full autodetect suite). Mixed Cargo repositories intentionally gain a new digest and first run cold. Config/auth and installed binaries relocate when CARGO_HOME is injected in every step: preserve project .cargo/config.toml, supply CARGO_REGISTRIES_* env auth, provision tools explicitly and use real toolchain binaries on PATH. No native config files are copied, read or rewritten. An explicitly external home is honored but requires shared mounts. Evidence: official Cargo home/environment references in research.md and real fetch with CARGO_HOME=.cache/cargo in research-tool.log.

## Limitations

Additional repository checks: `go test -count=1 ./...` returned failure outside the tool-local packages because this agent denies loopback TCP connections: harness HTTP tests and S3 mock endpoints reported `connect: permission denied`; GCS TestRoundTrip also could not reach 127.0.0.1:4443 (evidence/test-full.log). These are environment-blocked broad tests, not passes; the CI owner must rerun with loopback access and a GCS emulator. `go test -race -count=1 ./...` could not start because this environment has CGO disabled and no C compiler (`go: -race requires cgo; enable cgo by setting CGO_ENABLED=1`, evidence/test-race.log); the CI owner must rerun in a CGO-enabled toolchain image. Required CLI local/compatibility/public/build gates passed separately. `cache-intel.sh harness-core --tool cargo --worker-id w3 --branch feat/php-caching-support --jira ""` committed injection and assertions in six files at 2ecde6a1d3685c4396ed5663de38c918292d06e7 on feature/cache-intel-cargo-env-w3; it does not execute the harness-core Java tests, so those remain for companion CI.

Root or one-level shortest lock only, following current engine; deeper projects and lockless libraries are unsupported. Cache only download/index data, not target, extracted sources, installed binaries or toolchains. Linux amd64 Cargo/rustc 1.85.0 is directly exercised; cross-compilation alone does not establish native Windows/macOS runtime support. Offline resolution is proven for the pinned crates.io fixture, not every private registry or git transport. git/db may be absent for crates-only projects and is gracefully skipped; private dependency source and repository URLs require access-controlled storage and must not embed credentials in URLs. No concurrent snapshot during Cargo writes. No linker is available, so full project compilation is not claimed; dependency resolution/metadata is exercised. Performance and archive sizes must come from the CLI public gate, not an assumed speedup. Evidence: research-tool.log, baseline.log, official Cargo documentation and forthcoming CLI gate logs.

## Rollout and rollback

Release through the normal drone-cache release. Projects that start being detected get a new composite key, so their first run after rollout is cold. Roll back by reverting the mapping entry and preparer; an image rollback alone does not reuse keys created by this change.
